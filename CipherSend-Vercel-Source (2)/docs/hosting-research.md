# CipherSend hosting evidence

Research checked 2026-11-21. Vercel's current documentation says WebSockets are available on all plans and each connection remains pinned to one Function instance, but new connections and reconnects are not guaranteed to reach the same instance. It recommends external state for shared rooms and pub/sub. CipherSend deliberately avoids a permanent coordination store, so the chosen in-memory signaling service is a separate single-process service. Source: [Vercel WebSockets](https://vercel.com/docs/functions/websockets), last updated 2026-08-10.

Render supports WebSockets until the serving instance shuts down. Its load balancer assigns new connections randomly across instances, so the signaling process must stay at one instance while rooms live only in memory. Render's documented web-service setup binds to `0.0.0.0` and the platform `PORT` (default 10000); the Blueprint schema supports `numInstances: 1`, `buildCommand`, `startCommand`, `healthCheckPath`, and `envVars`. Sources: [Render WebSockets](https://render.com/docs/websocket), [Render Web Services](https://render.com/docs/web-services), and [Render Blueprint Spec](https://render.com/docs/blueprint-spec).

CipherSend's service health-checks `/healthz`, accepts WebSocket connections at `/ws`, allows only explicitly configured browser origins, and avoids writing room IDs, candidate data, IP addresses, or file data to its own logs. This does not prevent hosting, proxy, STUN, browser, or network infrastructure from processing transient connection metadata. Render restarts clear all process-local rooms and can interrupt signaling; no active session is durable.
